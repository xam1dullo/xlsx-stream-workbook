Architecture · xlsx-stream-workbook

How a workbook actually gets written

Two phases with a filesystem between them. Every behaviour that surprises people in this library — why a second save fails, why you cannot delete the temp files, why adding sheets in parallel is safe — falls out of that one decision. The parts, relationships and content types below were checked against the spec, not assumed.

Why a filesystem sits in the middle

  • A sheet becomes durable the moment it is added. The rows are gone from memory whether or not you ever save.
  • Sheets are independent, so Promise.all over addSheet is safe — file identity comes from a counter, never a timestamp.
  • Nothing holds the whole workbook, so writing a million rows costs the same memory as writing ten.

What the merge actually does

  • Carries the package parts from the first sheet forward: styles, and whatever else the writer emitted.
  • Writes one workbook.xml and one relationship set, numbering sheets in the order they were added.
  • Derives content types from the parts actually shipped. An unrecognised part is a hard error, not a guess.

What lands in the file

  • [Content_Types].xml · _rels/.rels · xl/workbook.xml
  • xl/_rels/workbook.xml.rels
  • xl/worksheets/sheet1..N.xml — one per sheet, copied verbatim
  • xl/styles.xml — carried from the first sheet
  • No shared strings, no theme, no docProps

How a reader finds a sheet

  • _rels/.rels → xl/workbook.xml, required of every package
  • workbook.xml.rels → sheet1.xml as rId1, sheet2.xml as rId2 — explicit: the r:id is written into the XML
  • → styles.xml as rId3, past the sheet ids so it cannot collide — implicit: inferred from the relationship type

Where the memory goes

  • Writing is backpressured, so peak memory does not grow with row count.
  • The merge is not: jszip assembles the archive in memory, so peak is roughly the size of the finished file.
  • For true end-to-end streaming, exceljs's streaming writer is the better tool. This library trades that for a much smaller surface.

Spec-required versus verified

Three of the things this library guards are required by ECMA-376. Two are not, and the difference matters if you are deciding whether to change them.

ConcernThe spec saysConfidence
A declared sheet whose r:id resolves to no part Required — Part 1 §12.3.24 Spec violation, guarded twice
A part on the generic xml Default OPC-legal (§7.2.3.2.1); the specific media type is normative for SpreadsheetML (§12.3) Stricter than required, deliberately
Non-finite <v> under t="n" Schema-valid — ST_Xstring is a string — but t="n" promises a number (§18.18.11) Sound derivation; Excel behaviour undocumented
Inverted spans on a row No constraint at all — §18.3.1.73 marks it "purely optional"; the schema is a bare string Observed Excel behaviour only
